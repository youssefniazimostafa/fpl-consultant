⚽ Methods & track record

← back to the verdict

How this site turns raw FPL data into a weekly verdict, and how well it's actually done so far. Every number below is produced by code in this repo -- no step is manual except the mid-week config edit and the rival squad transcription (private league, no API access to rivals' picks).

Data sources

  • Official FPL API (bootstrap-static, fixtures, entry/<id>/history) -- every player's price, ownership, status/flags, and the fixture list. The source of truth for gameweek resolution (the latest finished event) throughout, never hardcoded.
  • The Odds API -- match-result odds, converted to a clean-sheet / goals-scored probability per team per fixture, when a key is configured and the match is covered.
  • ClubElo -- a team-strength Elo rating, blended with recent underlying numbers into a fixture difficulty estimate whenever the odds feed doesn't cover a match (friendlies, lower-profile fixtures early in a round) -- every fixture-driven number on the site is tagged with which of the two actually produced it.
  • Understat -- underlying xG/xA per player, blended with FPL's own history for the attacking side of the model.
  • Manual league snapshot (data/manual/league_snapshot.json + data/ manual_snapshots/<gw>.json) -- this is a private 10-manager league with no public league_id, so rivals' squads, captains and chips are hand-transcribed from the app each week and validated by a regression test (each squad's computed points must equal its leaderboard score) before anything downstream trusts it.

The xP model

Each player's expected points for a gameweek is a sum of components -- appearance, attacking returns, clean sheets/goals conceded, defensive contribution, saves, cards, and bonus -- each built from a blend of this season's recent form and last season's rate, recency-weighted with a 6-match half life (a match 6 games back carries half the weight of the most recent one) so a player's current run matters more than April. Fixture difficulty (from the odds/Elo blend above) scales the defensive/clean-sheet components per opponent.

Minutes (p_start)

A player's expected-minutes fraction comes from his recency-weighted start rate (same 6-match half life as the rest of the model, not a flat rolling average), then dampened when his team plays again inside 4 days of its last match -- a congestion proxy for rotation risk. This only sees Premier League fixtures (the FPL fixtures endpoint doesn't cover cup competitions), so true European/cup rotation risk is an acknowledged blind spot, not a solved one. Press-conference news overrides this directly: config.json's p_start_overrides lets a specific (player, value, reason, date) entry win over the model for news the data can't see yet (an injury update, a surprise line-up leak), and the site flags which overrides are new since the last run.

Bonus

Rather than a flat bonus-points-per-90 estimate, each player's expected bonus comes from simulating his BPS (bonus points system) rank within his own match: his expected BPS is drawn with Monte Carlo noise (empirical standard deviation from two seasons of real match-level BPS data) alongside every other player in that fixture, and the top three simulated ranks convert to the real 3/2/1 bonus. Summing expected bonus across every player in a gameweek lands on exactly 6 × number of fixtures (3+2+1 per match) when the math is right -- a check this model passes.

Effective ownership & strategy

League EO is each rival's ownership weighted toward the managers closest to you in the table (the ones actually fighting for the same rank), not flat league-wide ownership. config.json's strategy mode (chasing/protecting/balanced) shifts the transfer/captain optimiser's objective toward low-EO differentials when chasing, or high-EO template picks when protecting a lead.

Decision engine

Transfers, starting XI, captain and chip timing are one mixed-integer program (not a greedy swap search), solved over a multi-week horizon so it can spot the right week to make a move rather than just the best move available this week. A transfer is only recommended when it beats holding (while still allowing a later-week move instead) by a threshold of expected points over the whole horizon.

Simulation: P(finish 1st)

The optimiser above picks the highest-expected-points plan, which isn't always the plan most likely to finish top this gameweek once rivals are accounted for. The simulation draws thousands of Monte Carlo gameweeks -- each player's realised points ~ Poisson(xP), with every manager who owns a given player sharing that one draw (so shared picks like Haaland move together across squads, not independently) -- for my transfer plan, my hold alternative, and each rival's last-known squad carried forward unchanged (no visibility into rivals' actual transfers). It reports how often each of my candidate plans comes out on top, shown next to the optimiser's own highest-average-xP pick. This is deliberately scoped to this gameweek's rank, not a season-long title race (simulating the whole rest of the season is future work), and Poisson is a simplifying, admittedly under-dispersed, stand-in for FPL's real scoring distribution.

Rival transfer forecasting (not yet live)

A model to predict each rival's next transfer from their own habits is scaffolded (fpl/ rival_transfers.py) but deliberately not switched on: it needs several gameweeks of archived rival squads to learn a habit from, and only one archive exists so far. It'll switch on once enough history has accumulated.

Accuracy track record

Every post-gameweek run scores last week's saved predictions against what actually happened, split by error source (minutes, attacking returns, clean sheets/bonus, unmodeled categories), and logs it to a cumulative accuracy chart on the main page. The model is also benchmarked once against FPL's own ep_next and naive baselines (points-per-game, last-5-average) over a full prior season:
