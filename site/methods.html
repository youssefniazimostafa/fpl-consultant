⚽ Methods & track record

← back to the verdict

How this site turns raw FPL data into a weekly verdict, and how well it's actually done so far. As of Step 12 every number below is produced automatically from the official API on a schedule -- the only manual step left is optionally editing config.json (e.g. a news override, or a strategy mode override), and the site runs and republishes itself without anyone visiting it.

Data sources

  • Official FPL API (bootstrap-static, fixtures, entry/<id>/history) -- every player's price, ownership, status/flags, and the fixture list. The source of truth for gameweek resolution (the latest finished event) throughout, never hardcoded.
  • Official FPL league API (leagues-classic/<id>/standings, every rival's own entry/<id>/event/<gw>/picks) -- with league_id set in config.json (the default, live mode), rivals' squads, captains, chips and standings are fetched automatically every run, with no manual transcription. Every run also cross-checks league_history's cumulative totals against the standings endpoint's own numbers (fpl.league.validate_standings) and stops with a clear error rather than publish anything that doesn't reconcile with the league's own scoreboard.
  • The Odds API -- match-result odds, converted to a clean-sheet / goals-scored probability per team per fixture, when a key is configured and the match is covered.
  • ClubElo -- a team-strength Elo rating, blended with recent underlying numbers into a fixture difficulty estimate whenever the odds feed doesn't cover a match (friendlies, lower-profile fixtures early in a round) -- every fixture-driven number on the site is tagged with which of the two actually produced it.
  • Understat -- underlying xG/xA per player, blended with FPL's own history for the attacking side of the model.
  • Manual league snapshot (fallback only) (data/manual/league_snapshot.json) -- for a genuinely private league with no resolvable league_id, rivals' squads can still be hand-transcribed and validated by a regression test (each squad's computed points must equal its leaderboard score). When a league_id is also set, the live API wins outright and the snapshot is only cross-checked against it as a staleness warning, never a blocker.

The xP model

Each player's expected points for a gameweek is a sum of components -- appearance, attacking returns, clean sheets/goals conceded, defensive contribution, saves, cards, and bonus -- each built from a blend of this season's recent form and last season's rate, recency-weighted with a 6-match half life (a match 6 games back carries half the weight of the most recent one) so a player's current run matters more than April. Fixture difficulty (from the odds/Elo blend above) scales the defensive/clean-sheet components per opponent.

Minutes (p_start)

A player's expected-minutes fraction comes from his recency-weighted start rate (same 6-match half life as the rest of the model, not a flat rolling average), then dampened when his team plays again inside 4 days of its last match -- a congestion proxy for rotation risk. This only sees Premier League fixtures (the FPL fixtures endpoint doesn't cover cup competitions), so true European/cup rotation risk is an acknowledged blind spot, not a solved one. Press-conference news overrides this directly: config.json's p_start_overrides lets a specific (player, value, reason, date) entry win over the model for news the data can't see yet (an injury update, a surprise line-up leak), and the site flags which overrides are new since the last run.

Bonus

Rather than a flat bonus-points-per-90 estimate, each player's expected bonus comes from simulating his BPS (bonus points system) rank within his own match: his expected BPS is drawn with Monte Carlo noise (empirical standard deviation from two seasons of real match-level BPS data) alongside every other player in that fixture, and the top three simulated ranks convert to the real 3/2/1 bonus. Summing expected bonus across every player in a gameweek lands on exactly 6 × number of fixtures (3+2+1 per match) when the math is right -- a check this model passes.

Free transfers, automatically

Every manager's free-transfer count is walked from their own full transfer history (fpl.league.build_free_transfers_table): start the season on 1, bank +1 per gameweek with no transfer made (capped at the usual limit), reset to 1 the gameweek after a hit was taken, and Wildcard/Free Hit leave the bank untouched. This replaced a hand-typed free_transfers/transfers_made pair in config.json that had to be updated every week and was easy to get wrong (an earlier run of this exact computation caught its own stale manual value out by 2). config.json's free_transfers_override stays available for the rare week the computed number and the real in-app number disagree (e.g. an API lag right after a deadline).

Rival window

Not every manager in the league is actually relevant to a given recommendation -- a team 400 points back can't be caught and can't catch you. fpl.league.build_rival_window_table flags every manager within rival_window_points (config.json, either direction) as "in window" each gameweek, recomputed fresh every run from live standings (never cached), and reports what the window would be if sized off the league's own recent scoring spread instead, as a sanity check. Squad-overlap threats, ownership and EO feeding the differentials/threats panels all prefer this window over the whole league once it's non-empty -- a player nobody in your actual title fight owns is a real differential, even if he's template two leagues down.

Gameweek snapshot archive

fpl.league.write_gw_snapshots writes one data/league/gw<N>.json per finished gameweek the first time it's seen -- a point-in-time record of every manager's total, rank, free transfers and any chip played that week -- and never rewrites a file for a gameweek that already has one, since a finished gameweek's standings don't change again. The very first run backfills every finished gameweek at once; after that, one new file lands per week. This is what gives the season simulation and rival-habit models something to learn from beyond this run's single live snapshot.

Effective ownership & strategy

League EO is each rival's ownership weighted toward the managers closest to you in the table (the ones actually fighting for the same rank), not flat league-wide ownership. config.json's strategy mode (chasing/protecting/balanced) shifts the transfer/captain optimiser's objective toward low-EO differentials when chasing, or high-EO template picks when protecting a lead, and is picked automatically each run from your points gap to first and the gameweeks remaining (fpl.league.determine_strategy) unless overridden.

Decision engine

Transfers, starting XI, captain and chip timing are one mixed-integer program (not a greedy swap search), solved over a multi-week horizon so it can spot the right week to make a move rather than just the best move available this week. A transfer is only recommended when it beats holding (while still allowing a later-week move instead) by a threshold of expected points over the whole horizon.

Simulation: P(finish 1st)

The optimiser above picks the highest-expected-points plan, which isn't always the plan most likely to finish top this gameweek once rivals are accounted for. The simulation draws thousands of Monte Carlo gameweeks -- each player's realised points ~ Poisson(xP), with every manager who owns a given player sharing that one draw (so shared picks like Haaland move together across squads, not independently) -- for my transfer plan, my hold alternative, and each rival's last-known squad carried forward unchanged (no visibility into rivals' actual transfers). It reports how often each of my candidate plans comes out on top, shown next to the optimiser's own highest-average-xP pick. This is deliberately scoped to this gameweek's rank, not a season-long title race, and Poisson is a simplifying, admittedly under-dispersed, stand-in for FPL's real scoring distribution.

Season simulation: P(finish 1st by GW19)

The gameweek-level simulation above deliberately doesn't answer "who wins the league" -- that needs a coarser, season-long projection instead. fpl.simulation.simulate_season_standings draws each manager's remaining gameweeks from Normal(their own historical mean, their own historical std) (std floored at a minimum so a manager with little history doesn't get an artificial zero-variance advantage), sums to a target gameweek (19 -- roughly the season's halfway point), and reports how often each manager's simulated total beats everyone else's across 20,000 Monte Carlo draws. This is a team-level model, not a full squad/xP re-simulation of every future gameweek -- it trades precision for being cheap enough to run every week from the start of the season, and feeds directly into the chip panel's "season context" (a chip is worth more when it visibly moves this number, not just this week's score).

Rival transfer forecasting

This used to be scaffolded but switched off: with no league_id, the only history of rivals' squads was a single hand-transcribed snapshot, and one data point isn't a habit. Now that league_id pulls every manager's picks for every gameweek played so far, fpl.rival_transfers diffs each rival's squad between consecutive gameweeks to get their real transfer history, turns it into three habit numbers -- hit rate, how often an incoming player had just hauled ("chases form"), and how often an outgoing player was already flagged before being sold -- and predicts each rival's single most-likely in/out for the next gameweek with a plain-English reason attached (league_rival_transfer_forecast.parquet), or "no clear signal" when none of those signals fire. It's published as its own advisory table alongside (never folded into) the confirmed, standings-validated EO -- a forecast swap is by definition not yet a real pick. The dashboard also shows the underlying habit rates (league_rival_habits.parquet) and gameweeks of history behind each forecast, so a reader can judge for themselves how much to trust a prediction built on 2 gameweeks of data versus 20.

Fully automatic, anywhere

Step 12's second goal was dropping the last manual steps and making the dashboard usable away from a laptop. A scheduled GitHub Actions run does the whole pipeline -- fetch, league, rival transfers, scoring, optimiser, simulation, publish -- end to end with no one visiting the site, and a failed run simply leaves the previous site/data/latest.json in place rather than publishing a half-built one (nothing downstream ever trusts a partial write). The page itself is an installable PWA (manifest.json + a service worker caching the static shell) so it adds to a phone's home screen like a native app and keeps showing the last successfully fetched data if you open it with no connection. Every data table collapses into stacked cards instead of a sideways-scrolling table under ~640px wide, and a status strip at the top -- current/next gameweek, your free transfers, and the next deadline converted to US Eastern client-side via Intl.DateTimeFormat (so EST/EDT just works, no hand-rolled offset) -- answers "what do I need to know right now" without reading a single panel. Staleness itself is a client-side check: the page compares generated_at against your own clock and flags it if the data looks old, rather than the pipeline ever claiming to know "now" from a server that only runs on a schedule.

Accuracy track record

Every post-gameweek run scores last week's saved predictions against what actually happened, split by error source (minutes, attacking returns, clean sheets/bonus, unmodeled categories), and logs it to a cumulative accuracy chart on the main page. The model is also benchmarked once against FPL's own ep_next and naive baselines (points-per-game, last-5-average) over a full prior season:
